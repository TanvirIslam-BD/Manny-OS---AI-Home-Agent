# Product and Hardware Assumptions

The following remain unresolved and must not be encoded as permanent hardware facts:

- The board is a Raspberry Pi 5 8 GB with NVMe (ADR-021). There is little memory margin: the default model occupies 5.24 GB on disk against roughly 6.3 GB of RAM left for it, and it still runs as a mmapped working set paged from NVMe. Whether that working set is small enough in practice is unmeasured until `ollama ps` is read on the device.
- Final display manufacturer, native resolution, touch interface, and rotation are not selected.
- Final camera model, field of view, and enclosure position require validation.
- Final microphone array, speaker, amplifier, and selectable device identifiers are unknown.
- LED controller, rotary encoder, button, privacy switch, and GPIO mappings are unknown.
- The configured Money Copilot MCP server advertises OAuth 2.1 authorization with `mcp:tools`, `mcp:resources`, and `mcp:prompts`; enclosure pairing still requires device validation.
- On-device token protection is bounded by hardware, not software. The Pi keeps OAuth material in a mode-0600 file because a headless appliance cannot hold a vault key anywhere the device itself cannot reach, and Pi 5 has no TPM or secure element to bind one to (ADR-013). Whether the enclosure gets such hardware is unresolved; until it does, physical possession of the device is possession of the Money Copilot session, and loss is handled by server-side revocation.
- The current MCP catalog has validated budget and spending schemas but no recurring-payment tool; recurring data remains unavailable rather than inferred.
- whisper.cpp base, eSpeak NG, Moonshine, Kokoro and the served conversational model have adapters but still require Raspberry Pi 5 latency, memory, thermal, pronunciation and per-language accuracy benchmarks *together*. Google's own Pi 5 figures for Gemma-4-E2B on LiteRT-LM give the model in isolation — 8 tok/s decode, 133 tok/s prefill, 7.8 s to first token, 1,546 MB peak memory — which is the model alone, not the model beside whisper, eSpeak, a kiosk browser and the camera.
- `gemma3n:e2b` is the device default for conversation and image understanding, at 5.24 GB. `gemma4:e2b` is the better model of the same class and the intended destination, but its model layer is 6.67 GB, which exceeds the roughly 6.3 GB an 8 GB board has left once the desktop session, kiosk, core and whisper have taken their share - so it can only run as a partially resident mmap and is a documented switch rather than the default (ADR-021). All sizes were read from the Ollama registry manifest rather than estimated; `gemma4:e4b` is 8.95 GB and no smaller quantisation of either is published. What is unmeasured for either model is the resident size in practice, which `ollama ps` reports on the device, and intent-routing accuracy against real utterances.
- The conversational model, Whisper, eSpeak NG, and browser/OS voices cover different language sets. Text works wherever the model is capable; voice availability and quality depend on the installed runtime and voice, so “all languages” is broad best-effort coverage rather than a universal accuracy guarantee.
- Desktop development uses mock hardware while finance values come from validated MCP data; physical acceptance remains pending.
- On-screen text entry covers Latin letters, digits and punctuation only. Chromium on Linux ships no virtual keyboard, so the kiosk supplies its own, but a Bengali or Chinese layout is not a larger version of the same component — those need conjunct composition and an input method. On a device whose default recognition language is bn-BD, voice is the input path for those scripts and typing is the Latin fallback. Adding an OS-level IME to the kiosk session remains open.
- Display rotation is configurable in `Settings` but nothing applies it, and rotating a touchscreen also requires rotating its input through the X11 coordinate transformation matrix. Only rotation 0 is supported until a rotated panel exists to calibrate against.
- Speech recognition stays on whisper.cpp even though Gemma 3n and 4 accept audio natively, and there is now external evidence for that rather than only reasoning. Google's own AI Edge Gallery exposes `llm_chat`, `llm_prompt_lab` and `llm_ask_image` for Gemma-3n-E2B — image input, but no audio task at all. So even in Google's reference application the audio encoder is not surfaced. The original reasons also still hold: the device default is bn-BD, `_whisper_language` exists because auto-detection mishears Bengali on short chunks, and routing audio straight to the model would remove the transcript as a separately validated, redactable artifact.
- LiteRT-LM was measured against this project and rejected, so it is no longer an open question. Its OpenAI server does support schema-constrained output through llguidance, routing was correct on all five intents with the real system instruction, the finance boundary held, streaming is compatible, and the model is 2,468 MB against Ollama's 6.67 GB. But `litert-lm serve` creates a conversation per request, so it re-prefills the system instruction every turn - three identical requests took 10.9, 10.8 and 10.7 seconds - which would add roughly 5.7 seconds per turn on a Pi 5 and defeats the prompt cache the adapter is written around. Its Python API would not have that problem, but using it means writing a local service rather than changing a base URL.
- Vision is real rather than theoretical for this model family: Google's AI Edge Gallery lists `llm_ask_image` for both Gemma-3n-E2B and E4B. Whether Ollama exposes it for the tag Manny pulls is a separate question that still needs `ollama show` on the device.
- Quantised builds differ enormously by packaging, which matters when budgeting memory. The same Gemma-3n-E2B is 3.14 GB as Google's int4 build and 5.24 GB as the Ollama tag; Gemma 4 E2B is 2.47 GB as a LiteRT-LM build and 6.67 GB as an Ollama GGUF. Any size figure has to name the artefact it measured.
